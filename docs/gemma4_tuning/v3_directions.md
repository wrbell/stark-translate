# Gemma 4 Tuning — What I'd Try Next

Honest forward-look written immediately after Phase D landed at parity-with-prod (`v1_results.md` "v2-cpo" section). The v1 → v1.1 → v2-cpo trajectory closed 88% of the COMET-22 gap to stock E4B but never crossed it. This doc lists what would actually move the needle, ordered by expected ROI per dollar / day of effort.

The brutal premise: **stock Gemma 4 E4B is already a strong EN↔ES translator**, and the v2 holdout (formal Spanish reference set: RVR1909 + Platense) is a hard target — a sermon-domain model that translates more naturally than the references will lose on COMET-22 against those references. Some of the apparent ceiling is the model genuinely being close to optimal for the constraints we set; some is a measurement artifact; some is real headroom we didn't exploit. The list below tries to separate which is which.

## Tier 1 — high leverage, low cost (do first)

### 1. Few-shot disambiguation in the production system prompt
**Cost:** ~1 hour. **Impact:** likely fixes 1-2 canary failures (Jacobo, partimiento del pan).

The Jacobo / Santiago disambiguation is genuinely a context problem the model can't solve from a flat training pair (both are valid). But Gemma 4's instruct mode can solve it from in-context examples. Prepend 3-5 hand-crafted examples to the production prompt:

```
Translate "James and John, sons of Zebedee" → "Jacobo y Juan, hijos de Zebedeo"
Translate "the book of James" → "el libro de Santiago"
Translate "the breaking of bread" → "el partimiento del pan"
[then the actual user request]
```

Cost is small at runtime (a few hundred extra tokens per request). Operator can A/B in `engines/llamacpp_engine.py` by adjusting one string. Doesn't require any retraining and can be reverted instantly.

### 2. Inference-time re-ranking
**Cost:** ~3-5 days engineering. **Impact:** real but adds latency.

Generate 4 candidates per source at temp=0.7 (same as Phase D), score with a CometKiwi distillation that fits in <500MB VRAM (e.g. wmt22-cometkiwi-da loaded once at startup), return the best. This is exactly what Phase D's preference triples were doing, but at *inference time* against the live source — no re-training, no preference data scaling needed.

The catch: 4× generation cost = ~4× latency. Acceptable for finals (the slow path) but breaks partials. Could be opt-in per request.

### 3. Targeted preference triples for the failing canaries
**Cost:** ~2-4 hours of native-Spanish-speaker time + ~2 hours engineering. **Impact:** fixes specific known failures.

Hand-craft 50-100 (chosen, rejected) triples for the disambiguation cases the canary tests probe (Jacobo vs Santiago, partimiento vs ruptura, etc.). Run a short CPO refinement on top of v2-cpo (lr=1e-6, 1 epoch, ~10 min). Targeted fix for a targeted symptom.

If a Spanish-speaking reviewer doesn't have time, the chosen/rejected pairs can be auto-generated by querying GPT-4 / Gemini with the disambiguation prompt and using its answer as the chosen, then a deliberately-mistranslated rejected.

## Tier 2 — substantial work, substantial impact

### 4. Human-translated parallel sermon data
**Cost:** $200–2000 for 200–1000 sermon chunks via professional service or volunteer pool. **Impact:** raises the ceiling on every future iteration.

This is the single biggest data gap. **All sermon "ground truth" we trained on (S1-S9 and v1/v1.1) was synthetic** — DeepL or 12B-distilled. v2-cpo's CometKiwi-XL preference signal was filtering synthetic pairs, not pulling from real human translations. A 200-chunk pool of native-Spanish-speaker translations would:

- Replace the noisy DeepL "ground truth" in C0's QE filter step (true human reference vs. cleaned-up DeepL)
- Provide *real* reference text for the COMET-22 eval (currently RVR1909 + Platense, both formal/biblical and not sermon-style)
- Build a much higher-quality preference triple pool (the human translation IS the chosen, the model output IS the rejected)

The current eval underestimates how good v2 already is on actual sermon Spanish — we're scoring against the wrong references. With proper sermon refs, v2 might already beat prod.

### 5. Larger preference pool (20K+ triples) + multi-cycle CPO
**Cost:** ~12-15 hr GPU + ~$50 in COMET API credits if scaled past local CometKiwi. **Impact:** plan-claimed +0.5-1.5 COMET; we'd see somewhere in that band.

Phase D used 1,384 triples × 1 epoch — by ALMA's findings, that's the floor. The paper's headline numbers came from 5K+ triples × 2 cycles. Worth doing once the human refs are available (Tier 2.4), since they upgrade the chosen side of every triple.

ARPO/X-ALMA isn't indicated for v3 — Phase D didn't show CPO over-rejection. Don't switch optimizers; scale data.

### 6. Eval rebuild with multi-reference + hand-crafted sermon refs
**Cost:** 1-2 weeks of native-speaker time. **Impact:** changes what we're measuring more than what we're shipping.

The 500-verse v2 holdout uses single-reference COMET against RVR1909 (or Platense). COMET-22 punishes ANY paraphrase that doesn't match the reference exactly — even a better translation that happens to use different words. Multi-reference COMET (per WMT 2025 best practice) and a sermon-style reference set would more honestly measure what v2 actually does.

This might *show* that v2 already beats prod once the eval is fair — making Tiers 1-3 ship-ready without further training.

## Tier 3 — different angles entirely

### 7. Switch to a translation-specialized base
**Cost:** 2-4 weeks of work, including production engine rewiring. **Impact:** different ceiling, different trade-offs.

Gemma 4 E4B is a generalist instruct model. Translation-specialized bases (X-ALMA-13B, Llama-3.1-8B-MT, NLLB-200) start from a higher floor on translation specifically. The trade is:
- X-ALMA-13B: probably +2-5 COMET-22 over our v2 ceiling, but 13B = ~7 GB Q4_K_M = doesn't fit on RTX 3060 12GB and pushes A2000 16GB to the limit
- NLLB-200: lower individual translation latency, but no chat template / instruct interface — would require complete rewiring of the operator UI prompt path

This is a bigger architectural commitment than the SFT+CPO loop, but the only path to substantially better translation quality from this hardware tier.

### 8. Larger Gemma 4 / Gemini-style base
**Cost:** depends on hardware. **Impact:** likely meaningful, costs runtime budget.

Gemma 4 E4B at 4B effective params is already hitting our quality ceiling. Bumping to a 27B-class model would shift it. Doesn't fit on A2000 16GB at Q4_K_M (~16GB needed); needs RTX 4090 or A100. Production wall-clock latency per request would 2-3× — breaks the live partials latency budget.

Not the right move unless production hardware also gets bumped.

## Tier 4 — measurement / process changes (no model work)

### 9. Live-session A/B framework
**Cost:** ~1 week. **Impact:** changes how we know if anything we ship works.

The COMET-22 holdout eval is a proxy. The actual question is "does the operator hear better Spanish during live services". Build:

- Two GGUFs loaded simultaneously on llama-server (separate ports)
- Operator UI gets a "swap engine" toggle that flips between them mid-session
- Each translation logs which engine produced it + a "flag this" button
- Post-session report: per-engine flag rates, operator subjective notes

If v2-cpo wins live A/B even though it ties on COMET-22, that's the answer that matters for production. If it doesn't win, we have direct user evidence to stop pushing the SFT+CPO loop and pivot.

### 10. Glossary-forced decoding via llama.cpp grammar
**Cost:** ~2-3 days. **Impact:** deterministic disambiguation but only for terms in the grammar.

llama.cpp supports GBNF grammars that constrain output. Could enforce Jacobo vs Santiago disambiguation deterministically based on EN context detection at request time (regex-detect "James and John" / "sons of Zebedee" → force Jacobo grammar; default to Santiago). Brittle but deterministic.

Less elegant than Tier 1.1 (in-context examples) but doesn't depend on the model picking up the prompt cue.

## Recommended sequencing

If you came back next week with $500 and a free week:

1. **Tier 1.1** — few-shot disambiguation in the prompt. 1 hour. Probably fixes the canary regression standalone.
2. **Tier 2.4** — pay for 200 sermon chunks of professional human translation. ~$200, ~1 week turnaround. This is the single most valuable data investment.
3. While waiting for the translations, run **Tier 4.9** — build the live A/B framework. ~1 week.
4. When the translations land, redo the QE filter + COMET-22 eval with proper sermon refs (**Tier 2.6**). This might already show v2-cpo wins; if so, ship and stop.
5. If still tied or losing, run **Tier 2.5** — scale preference triples to 20K using the human refs as the chosen side, retrain CPO 2 cycles.

Total cost for steps 1-5: ~$200 + ~3-4 weeks of engineering. Realistic ceiling improvement: probably +0.005-0.015 COMET-22, plus the live-A/B framework which is independently valuable.

If you came back next quarter with $5K and 2 months:

Same as above, plus **Tier 3.7** — port to X-ALMA-13B as a parallel track, comparing against the v2-cpo ceiling on the new eval. The 13B model will need RTX 4090 / A100 to deploy in production at our latency budget, which is probably a separate hardware purchase decision.

If you came back with no budget, just genuine curiosity:

**Tier 1.1 + Tier 4.9** — 1-2 weeks of work, no model retraining, no spending. Ship the few-shot prompt change, build the A/B framework, and just *measure* whether v2-cpo (or any future iteration) actually helps the operator vs stock E4B. That's the question that's been unanswered all along.
